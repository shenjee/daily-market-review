## 1. 使用场景与现状

- Supabase 项目 `nyscgdxrctwchbzclszt` 已创建，地域选择 Auto，实际分配地域待控制台核对，不能从 Auto 推断。

### 1.1 必须支持的使用流程

1. 权威账本是同一个 Supabase 项目。各机器把本机 SQLite 显式上传；第二台上传时云端已有数据也必须支持。不建立两机互相同步，不要求两份日常库持续一致。
2. 任一机器都可以把云端完整下载到一份本地 SQLite。这是按需能力，不是切换前必须把云端拉回每台日常库，也不是两机基线一致的门槛。下载前备份，并保护尚未上传的本地内容。
3. 新版本日常命令默认使用 Supabase；没有云端配置时明确报错，不静默使用本地数据。
4. 用户可用 `--backend sqlite` 明确选择本地读写；`--db` 只指定本地文件，不能把默认后端改成 SQLite。本地新增或修改仍能通过显式上传进入云端。

第 6 项迁移已在交付时点 revision 42 独立通过。第 7 项默认切换仍未通过，#10 不关闭。使用者通过 Agent 调用 Skill。跨机器仍由用户协调排他写入；上传和下载不是后台自动复制，也不承诺自动解决两边冲突。冲突策略采用下文保守基线，实际冲突的取舍由用户决定，不能按机器时钟替用户选值。

## 2. 保留业务模型与接口

保留五张业务表：

| 表 | 业务约束 |
| --- | --- |
| `daily_market_review` | 一个交易日一行，交易日唯一 |
| `daily_price_limit_event` | 日期、市场、代码、方向联合唯一 |
| `daily_price_limit_event_detail` | 对应事件的明细标量，关联事件 |
| `daily_price_limit_event_sector` | 每条事件的有序板块列表 |
| `daily_price_limit_event_reason` | 每条事件的有序涨停原因列表 |

字段、单位、合法值和 patch 语义以现行代码、[数据库设计](数据库设计.md)、[数据字段与口径](../references/数据字段与口径.md) 为准。尤其保留：未提供字段不变、显式 null 清空、0/false 有效、列表整体替换、空列表清空、列表顺序及去重语义、空批次 no-op、事件更新保留明细、删除关联清理和方向替换语义。金额精度和布尔编码保持现行合同。

PostgreSQL 中日期、时刻和审计时间戳均使用文本，保留现行格式；金额、价格、比率使用 `double precision`，数量与高度等使用整数。`is_leader` 使用可空整数并约束为 `1/0/null`；`closed_at_limit` 使用非空 `1/0`。读取后恢复现行 Python 的 `float`、`int`、`bool`、`None`，再进入 summary 和 ladder。浮点对照统一使用 `math.isclose(rel_tol=1e-12, abs_tol=1e-9)`，空值、整数和布尔严格比较。

保留 CLI 命令、输入输出及错误合同的可兼容部分。Skill 通过统一 CLI 调用。业务校验、交易日历、summary、ladder 和缺失字段计算保持共用；统计与展示在读取时进行。

前交易日由交易日历确定，不能用上一条有数据的日期替代。按交易日和跨日读取均须覆盖现有 repository/service 的依赖；分页不可截断记录。优先保留现有唯一键及关联约束，额外索引按真实查询验证后决定。

## 3. 接入与事务

```text
Skill / Agent
    → 统一 JSON CLI 与业务校验
    → 存储适配层
        → SQLite（保留原有本地能力）
        → urllib / HTTPS → Supabase Data API → PostgreSQL
    → 共用读取统计与展示
```

- Python 运行时仅使用标准库 `urllib`、`json` 等，通过 HTTPS 调用 Data API。
- Supabase Data API 路径前缀为 `/rest/v1/`，数据库函数使用 `/rpc/<function_name>`。
- 自己控制的本机后台程序采用新版 Secret Key（通常以 `sb_secret_` 开头），通过 `apikey` 请求头传递。
- 数据库密码与 Secret Key 是不同凭证。数据库密码可用于管理和备份工具，不是日常 HTTP API 的密钥。

### 3.1 完整读取与 HTTP 次数

采用**完整 JSON 读取 RPC**，不采用客户端逐表分页。函数返回单个 `jsonb` 对象，不能返回 `SETOF` 或表行集；在一个 SQL 语句的同一快照中聚合完整结果，不在聚合前加隐含 LIMIT。Supabase 默认最多返回 1000 行，因此不能直接把普通表查询或行集 RPC 当作全量结果（见官方读取参考）。

- CLI `get`：一次读取 RPC，参数包含目标交易日、由客户端交易日历计算的前交易日、预期 schema 版本。一次返回当日复盘、事件、明细、板块、原因以及前交易日事件；客户端复用现行统计逻辑。
- repository 的单日或跨日 `get/list` 方法：每次方法调用一次对应读取 RPC；包含起止日期（边界含当日，省略表示不限）及预期版本，所需关联数据一次拉齐。`list_reviews` 不循环按日请求；`list_trade_dates` 仍只列总体复盘表中的日期。
- 返回对象含 `schema_version`、`complete=true`、各数组及各自完整查询的总行数；空数组明确为 `[]`。客户端检查必需键、计数、业务键唯一性、顺序和关联完整性。任何缺项、计数不符、截断 JSON、超时或大小限制均整次报错，不生成部分 summary/ladder，不将失败当作无数据。
- 数组按现行日期及事件身份排序，多值按 `position` 排序。当前数据量不设静默截断；以后若需分块，另行设计快照与完整性协议。
- 每次读 RPC 内核验版本，无须额外版本 HTTP 请求。正常非空日常写命令是一次写前读取加一次写 RPC，共两次 HTTP；普通写入使用轻量活性读，`replace-direction` 使用同时检查活性、版本并取得前像的专用读取 RPC（见第 4 节），不再另发活性请求。失败核验和显式重试另计。

### 3.2 写入参数与 patch

下列七类日常写函数统一接收一个具名 `jsonb` 参数 `p_request`，HTTP 请求体为 `{"p_request": {...}}`。内部共同字段为 `schema_version`、`trade_date`、`batch_time`；函数名实现时确定，以下业务载荷形状固定：

| 操作 | 共同字段之外的载荷 |
| --- | --- |
| `save-review` | `fields`：仅包含本次提供的原子字段 |
| `save-events` | `events`：完整事件对象数组，沿用现行必填字段与校验 |
| `save-event-details` | `details`：事件身份及本次提供的明细字段组成的对象数组 |
| `delete-event` | `market`、`code`、`direction` |
| `replace-direction` | `market`、`code`、`old_direction`、完整新事件 `event` |
| repository `delete_review` | 无其他字段 |
| repository `delete_price_limit_events` | 无其他字段 |

例如明细 patch 的请求体：

```json
{
  "p_request": {
    "schema_version": 1,
    "trade_date": "2026-09-28",
    "batch_time": "2026-09-29T01:00:00+00:00",
    "details": [{
      "market": "sh", "code": "600519", "direction": "up",
      "note": null, "sectors": [], "is_leader": false
    }]
  }
}
```

这里清空 note 和板块、保存 false，其余字段不变。示例为协议说明，不用于正式写入。

JSON 对象的键是否存在是合同的一部分。数据库先用 `patch ? 'field'` 判断，再读取值；不得用 `COALESCE`、补齐缺失键或直接转整行记录消除缺失与 null 的区别。标量显式 null 清空，0/false 是有效值；列表 `[]` 清空，列表 null 按现行校验拒绝。未知字段、非法类型、重复事件身份整批拒绝。事件 upsert 是完整事件更新，不是明细 patch，不得修改明细或列表。

请求中的 `is_leader`、`closed_at_limit` 使用 JSON 布尔，不能把 `false`/`true` 提取成文本后直接转整数。函数先检查键是否存在及 `jsonb_typeof`：布尔值用显式分支映射 `true → 1`、`false → 0`；`is_leader` 的 JSON null 映射 SQL NULL，缺键保持不变；`closed_at_limit` 必填且不接受 null。字符串 `"false"`/`"true"` 和数字 `0/1` 均拒绝，不能依赖宽松类型转换。读取时将数据库整数还原为 JSON/Python 布尔，保留 `is_leader` 的 null。

### 3.3 事务与适配层覆盖

以上七类写操作各用一次 RPC，承接完整 SQLite 事务边界。除五个 CLI 写命令外，适配层必须覆盖 repository 已有全部读写方法；本次不因此新增两个按日删除 CLI 命令。

- 明细写入必须确认所有父事件存在；任一不存在，整批失败，包括已写的明细与列表全部回滚。
- 方向替换在同一函数中检查旧事件存在、目标方向不存在，读取旧明细与列表，删除旧事件，插入新事件，恢复原有明细行和板块；新方向为 down 时丢弃涨停原因。原先只有列表而无明细行时，不能凭空创建明细行。
- 删除单条或按日删除全部事件须同时清理关联明细、板块和原因，保留总体复盘；`delete_review` 仅删除该日总体复盘，保留事件。删除不存在的记录不报错。
- 数据库函数校验失败必须抛出错误，不能捕获异常后返回成功或提交部分数据。唯一键、外键、合法值约束与客户端校验共同生效。

### 3.4 时间戳合同

日常写入客户端完成校验后，为一个逻辑批次生成一次 UTC 秒级 `batch_time`，格式沿用 `utc_now_iso()`，如 `2026-09-29T01:00:00+00:00`。SQLite 与 Supabase 使用同一个注入时间；函数不得自行用数据库时钟重取时间。同一请求的重试保留原 payload 和 batch_time。

- 新复盘、事件或明细行的 created_at/updated_at 均为该批次时间。
- 冲突更新保留 created_at，仅将实际涉及的行 updated_at 改为该批次时间；事件 upsert 不刷新明细时间。
- 方向替换的新事件及原明细的重建行，两种时间均为替换批次时间，不保留旧 created_at。
- 仅更新板块/原因列表时，不创建明细行，也不刷新已有明细行时间；多值表本身没有审计时间列。
- 当前 SQLite `save_review` 内部创建和更新时间分别取时；实现适配层时须统一成一次注入时间，这是待实施调整。历史上传合并与全量下载走第 7 节专用同步协议，保留原时间，不补写成同步时间。

### 3.5 Schema 迁移与授权

SQL、函数及授权保存为版本化迁移文件。云端建表、升级及版本登记仅由显式管理命令使用数据库管理连接执行；日常 CLI 不执行 DDL。schema 版本元数据属于基础设施，不改变五张业务表模型。每个读写 RPC 均核验客户端预期版本，缺失或不一致就拒绝；写入前的活性读也检查版本。迁移期间停止所有日常任务，两台机器升级后再恢复。

新版 Secret Key 对应 `service_role`，不能仅依赖 RLS。迁移需撤销 `PUBLIC`（PostgreSQL 伪角色）、`anon`、`authenticated` 对业务表和业务函数的权限，只向日常服务角色授予所需 DML/EXECUTE，保留管理角色的维护权限。对迁移对象所有者设置后续对象的默认权限，防止新增函数重新公开 EXECUTE；版本/活性探针同样受限。函数优先 `SECURITY INVOKER`，固定安全 search_path 并显式限定表名；若确需 DEFINER，必须单独审查权限边界。密钥不得进入页面、仓库或发布包。

## 4. 配置与失败边界

后端选择优先级固定为：显式 `--backend` > 本机配置 `backend` > 默认 `supabase`。合法值只有 `sqlite`、`supabase`；非法值报错。选择 SQLite 时不要求提供 Supabase 凭证。

本机配置与凭证位置（由用户从仓库 / 发布包模板复制后自行填写，填好的内容不进 Git）：

| 内容 | 本机路径 | 仓库模板 |
| --- | --- | --- |
| `backend`、`supabase_url`、`supabase_publishable_key` | `~/.marketreview/config` | `config/marketreview.config.example` |
| Secret Key（单行，权限 600） | `~/.marketreview/supabase.secret` | `config/supabase.secret.example` |

项目 URL 与 Publishable key（`sb_publishable_...`，旧名 anon）为普通配置，可写在 `config`。Secret Key（`sb_secret_...`，旧名 service_role）单独保存在 `supabase.secret`，不得写入 `config`。兼容旧布局：仅当 `supabase.secret` **不存在**时，可读 `~/.marketreview/supabase.config` 中的 `SUPABASE_SECRET_KEY`（及其中的 URL）；文件存在但为空、格式无效或键值为空时直接报 `CONFIG_MISSING`，不回退旧密钥。安装时仅在目标文件不存在时从模板创建，已有文件对照模板手工补字段，不得覆盖。可用 `MARKETREVIEW_CONFIG_DIR` 覆盖配置目录（测试用）；`MARKETREVIEW_HOME` 只控制本地库路径，不选择后端、也不改配置目录。填写步骤见 README「云端配置模板」与 `SKILL.md`「云端配置」。

- 新版本未配置 backend 时默认 Supabase；缺 URL、密钥或断网均报错。这是有意改变旧版本默认行为，升级说明和 SKILL.md 必须明确说明，不能把现存 SQLite 文件当作自动回退理由。`CLOUD_DEFAULT_ENABLED=True`。选择顺序仍是 `--backend`、配置文件 `backend`、代码默认值。配置里的 `sqlite` 会盖过代码默认值，所以两机配置都要写成 `supabase`。
- 显式 `--backend sqlite` 可覆盖本机的 supabase 配置；SQLite 路径保留 `--db` > MARKETREVIEW_HOME > 默认路径的规则。`--db` 单独出现不能隐式选择 SQLite；最终有效后端仍为 supabase 时，与 `--db` 冲突，在打开库或请求网络前报错。
- MARKETREVIEW_HOME 只控制本地库路径，不选择后端。默认云端日常命令不得打开日常 SQLite；显式 SQLite 命令不得请求云端。
- 同步入口独立于日常 backend，显式指定本地来源/目标和云端项目，不修改默认配置。命令合同为 `sync push`（本地→云端）与 `sync pull`（云端→本地），分别用 `--source`、`--target` 指定 SQLite；省略时按现有本地路径规则确定日常库，输出解析后的路径和项目。实现见 `scripts/marketreview/sync_engine.py` 与 CLI `sync` 子命令。#11 已在同 Mac 双账本对真实项目完成上传合并与全量下载冒烟（含 PG jsonb 整值 float 归一化修复）；#9 与合同第 6 项迁移已通过。默认切换的开发侧记录见[环境实测记录](Supabase环境实测记录.md)。#10 在独立复查通过前不勾选、不关闭。
- Agent 使用默认云端；用户要求本地时使用 --backend sqlite；用户要求同步时走专用同步入口，不能循环调用日常保存命令搬运数据。

- 提供本地配置模板（见上表），由用户填写 URL、Publishable 与 Secret；凭证不得进入 Git、发布包、日志或测试夹具。
- 一次业务命令只使用一个后端。选定云端后，配置缺失、鉴权失败或断网均明确报错，不自动回退本地 SQLite，不双写。
- HTTPS 保持证书验证；不得向其他主机重定向转发密钥。错误输出须脱敏。
- 网络超时可能发生在提交之后。不得把超时等同于已回滚，也不得对全部写操作无条件重试。
- 空 fields/events/details 按现行校验顺序返回 no-op，不发活性读或写请求。
- 每次非空日常写入前做受限的只读 RPC，检查活性和版本；方向替换在这次读取中额外取得完整前像（步骤见下），其余写入使用轻量探针。失败则停止，不发写 RPC。长假后若项目已暂停，须先恢复到可读状态；不能保证一次请求会自动唤醒。这只能减少冷启动造成的未知结果。
- `save-review`、`save-events`、`save-event-details` 的同一绝对值 payload（含同一 batch_time），在排他写入持续成立且无后续覆盖写的前提下可有限重试；单条和按日删除亦可重试。收到确定的校验、鉴权或版本错误不重试。
- `replace-direction` 不盲重试。超时后用一次读取同时核验旧、新方向：旧在新不在，且旧内容与本次写前保存的前像一致，在已排除在途执行且排他写入持续成立时可重试；旧不在新在，须核对新事件、迁移明细、列表与时间戳，吻合才能确认成功；两者都在、都不在或内容不符，停止并报告结果未知。核验读取失败时也停止。
- 网络错误后的核验必须等待原请求可能仍在执行的窗口结束；读到旧状态不等于原请求已回滚，无法排除在途执行时不能重发方向替换。实现时以服务端语句超时上限和请求起始时间确定等待窗口；日常 Data API（Secret）路径按实测 **8 秒** 计（见[环境实测记录](Supabase环境实测记录.md)）。窗口内只允许停止并稍后核验；窗口结束后前像仍一致才可确认未执行并按第 4.1 节受控重发。
- 本机只要存在未关闭的待核验记录，所有后续写命令（包括 save-events、删除和另一次 replace-direction）均不得发送新的写 RPC，只允许对已有记录执行核验和受控恢复；方向替换先只读核验，同步 operation_id 的幂等恢复按第 7.2 节执行；普通读命令可以继续。此闸门在每次写命令入口检查，进程重启后仍生效，不能因更换命令或目标交易日而绕过。记录无法读取或损坏时同样阻止写入，不得当作没有记录。
- 核验确认成功或确认未执行/已回滚后，先持久化结果并关闭记录，才可恢复写入；确认未执行后如需重试，必须重新进入原请求的受控发送流程，保留原前像、payload 和 batch_time，并在发送前重新持久化未关闭状态。仍为结果未知的记录不得自动关闭、删除或用新前像覆盖。
- 该闸门仅保护本机，另一台机器看不到本机待核验记录，不构成云端锁。跨机器仍由用户协调排他写入：结果未知时先在原机器核验并关闭记录，再换机接续写入。

### 4.1 方向替换的写前快照与超时核验

1. 客户端校验输入并取得排他写入资格后，紧接写 RPC 之前调用一次专用只读 RPC。以日期、市场、代码、旧方向及目标方向为查询条件，在同一 SQL 快照中检查 schema 版本并读取两种方向的状态；该调用兼任活性检查。旧事件不存在或目标事件已存在时直接失败，不发送写 RPC。
2. 返回并保存旧事件全部存储字段（含 created_at/updated_at）、明细行是否存在及其全部字段（含时间戳）、板块和原因的完整有序列表（含 position），以及目标方向不存在的结果。响应沿用第 3.1 节完整性与计数检查。不能使用省略审计列的普通业务记录，也不能把“无明细行”和“存在一行全 null 明细”合并。
3. 发送前将前像、项目标识、schema 版本、原始请求 payload（含固定 batch_time）和请求开始时间保存为本机待核验记录；不含任何凭证，不进入仓库。保存失败则不发写请求。该记录用于进程退出后的稍后核验；成功或确认失败后标记结果。排他写入从读取前像一直保持到结果确认。
4. 写 RPC 仍在自己的事务内检查旧事件存在与目标不存在，并完成第 3.3 节全部步骤；写前快照只用于结果核验，不替代事务检查。超时后保留原前像，不用后续读取覆盖它。
5. 在第 4 节规定的在途执行边界下，用同一专用读取 RPC 获取两方向的完整现状，按以下两个分支核验。比较使用第 2 节统一类型及浮点规则。
   - **旧在新不在**：旧事件的全部字段、明细行存在性及全部字段（包括两者的 created_at/updated_at）、板块和原因的有序列表，均须与步骤 2 保存的前像逐项一致。符合全部重试条件并确认未执行/已回滚后，必须先持久化本次核验结果并关闭待核验记录；如需重试，再进入原请求的受控发送流程，保留同一份原记录的前像、payload 和 batch_time，在发送前将该记录重新标为未关闭并持久化，然后才可重发原请求。关闭、重新标为未关闭和发送必须在同一次连续持有 write.lock 内完成，中间不得释放锁；关闭或重新持久化失败均不得发送写 RPC；不得在上次待核验状态尚未关闭时直接重发。
   - **旧不在新在**：新事件的身份和业务字段与原请求一致；明细行存在性保持前像状态，若原有明细行，其业务字段与前像一致；板块的有序列表与前像一致；新方向为 up 时，原因的有序列表须与前像逐项一致（包括顺序），新方向为 down 时，原因列表须为空。新事件以及实际重建的明细行，其 created_at、updated_at 均须等于本次原请求的 batch_time，**不与前像中的旧时间比较**。原先无明细行时仍须无明细行。全部符合才能确认替换成功。
6. 缺失前像或待核验记录、读取不完整、排他写入被打断、内容不符或无法排除原请求仍在执行，均停止并报告结果未知，不自动重试，也不凭方向存在性单独宣告成功。

## 6. 实现验收

- 单日总体复盘 patch：遗漏字段、null、0 与重复写入。
- 约一百条事件的批量写入：唯一键更新、重复输入及原有明细保留。
- 明细、板块、原因一次提交：顺序、清空、关联及非法输入。
- 方向替换：目标身份冲突、关联迁移、涨停原因限制及时间戳合同；写前前像完整保存、仅两次正常 HTTP、前像保存失败时不写入、超时后前像丢失或内容变化时禁止自动重试，以及进程重启后沿用原前像核验。
- 方向替换成功核验使用不同于前像旧时间的 batch_time：旧方向消失、新事件和重建明细的两种时间均为 batch_time 时应确认成功；旧方向仍在的分支则必须保留前像时间，时间变化时不得重试。
- 未关闭待核验记录存在时，save-events、单条及按日删除、另一次 replace-direction 等全部写入口均不发送新写 RPC，跨日期及进程重启不能绕过；读命令和只读核验仍可执行。记录损坏时阻止写入，结果持久化关闭后才解除闸门。
- 方向替换确认未执行/已回滚后的重试顺序：先持久化核验结果并关闭记录，再保留原前像、payload 和 batch_time，将同一份原记录重新持久化为未关闭，最后发送写 RPC；任一持久化步骤失败均不得发送。
- 方向替换成功核验：新方向为 up 时原因的内容及顺序均与前像一致，为 down 时原因必须为空；顺序不符或残留原因不能确认成功。
- JSON 布尔 true/false 正确落为整数 1/0 并读回布尔；is_leader 的缺键/null 分别不变/清空；布尔字段的字符串、数字及 closed_at_limit 的 null 均整批拒绝。
- 删除单条事件、按日删除事件、仅删除复盘的隔离语义；空批次零 HTTP 请求，以及全部 repository 读方法。
- 超过 1000 条的跨日事件与多值记录完整读取；截断 JSON、计数不符、响应过大或超时必须报错，不能输出部分统计。
- 同一固定批次时间下核对所有审计列；schema 缺失或版本不一致拒绝，普通 CLI 不执行建表升级。
- 函数在批次中途失败时整批回滚，读回确认所有关联表无部分修改。
- 合法匿名 key 无法读写五张表、调用业务 RPC 或探针；authenticated 同样无权限。Secret Key 无效/吊销时的 HTTP 状态与错误体；权限错误与业务校验错误可区分，日志无凭证。
- 超时、连接中断、限流与安全重试。
- 同一数据集、同一交易日历及前日依赖下，SQLite 与 Supabase 的 get/summary/ladder、空值和排序一致。
- 默认 Supabase、显式 SQLite 覆盖及 --db 冲突行为正确；云端失败不触发本地读写；版本包仍可独立安装。

当前 Mac 为主备份机，文件存入 `~/.marketreview/backups/supabase/<UTC时间>/`；成功后复制到 M1 同路径作为第二份，文件不进入仓库。每份包含五表一致快照、结构、约束、索引、函数、授权、schema 版本、账本 revision、组历史、同步提交结果、对应迁移文件、行数清单和 SHA-256 校验清单。本地 SQLite 备份同时包含账本身份、共同基线及本地操作结果。导出需覆盖依赖对象，不得仅用五个 `--table` 参数遗漏函数。仅导出应用对象，不打包平台系统表或密钥；目标角色的映射与授权恢复步骤另存说明，不导出角色密码。

### 7.1 同步协议与合并规则

保留五张业务表；同步需要额外基础设施元数据，不把业务数据改成每日 JSON。实施前在共享协议 `contracts/supabase_rpc_v1.json` 固定快照、同步预检、提交、提交结果查询的函数名、请求/响应、格式版本及错误合同。

- 完整云端快照由一次只读 RPC 在同一条 SQL 的快照内返回五表、同步元数据、版本和计数，单 jsonb；截断或超限整次失败，禁止多次 get/按日列表拼接。管理工具可通过 #4 验证的管理连接，在一个只读 REPEATABLE READ 事务中取得同等快照，但不作为日常 Skill 同步的必需依赖。
- 合并单位：一日总体复盘是一组；同一日期/市场/代码的全部方向事件、其明细和有序板块/原因构成另一组，避免把方向替换误当作互不相关的新增与删除。不存在、无明细、全 null 明细及空列表均保留区别。
- 同步组是比较及提交单位，不改变五表主键或外键：事件主键仍包含 direction，总体复盘与事件仍独立。不会因为一个复盘组冲突而阻止同日独立事件组同步。
- 上传先读取本地一致快照 L、同一云端快照 C，以及该本地账本与该云端项目已确认的共同基线 B。业务相等按第 2 节比较：浮点用约定容差，身份、空值、明细存在性和列表顺序严格比较；created_at/updated_at 不用于判定哪边更新，但实际写入/下载须严格保留所选来源的时间。仅审计时间不同不算业务冲突，相同业务组保留云端时间并在报告中显示。

规则按组选择：该组有可信基线才使用三方表，没有基线则使用首次接入规则；不能因为其他组已有基线而把本组缺失当作已确认不存在。

下表及全文的 L=B、C=B、L=C 和不等判断，统一指上述**忽略审计时间的业务相等**，不是含 created_at/updated_at 的 group_payload 整包相等。摘要仅用于计划绑定和完整性校验，不能代替带浮点容差的业务比较。

**已有可信基线的三方比较（按顺序判定；pull 阻止项可由下述有效逐组授权解除）：**

| 条件 | push 行为 | pull 行为 |
| --- | --- | --- |
| L 与 C 业务相同（包括均不存在） | 不写业务，可确认该组新共同基线 | 可下载并统一审计时间 |
| L=B、C≠B：只有云端改变 | 不上传，报告“云端更新待下载”；不推进该组基线 | 可采用云端，包括云端删除 |
| C=B、L≠B：只有本地改变，L 存在 | 自动纳入上传集合，保留本地时间 | 停止覆盖，提示先上传或显式放弃 |
| C=B、L≠B：只有本地删除 | 不自动删除云端，报告“本地删除待处理” | 停止，需选择“把云端恢复到本地”或“在云端删除” |
| 两边均偏离 B 且彼此不同 | 冲突，保留两边并等待选择 | 停止，不能自动覆盖 |

**没有可信基线的首次接入：** L/C 相同可确认基线；仅本地存在且云端无相关删除历史可新增；仅云端存在时，push 归入无需上传，只报告“云端更新待下载”，不建基线、不阻止其他组提交；pull 可下载；两边都存在且不同则冲突。仅本地存在但云端有删除/方向替换历史时必须报冲突，不能自动复活。缺失基线不是“已确认不存在”，基线损坏或项目/账本身份不符不能当作首次接入悄悄重建。

- 预检输出三类集合：可提交组（自动合并、用户明确选择采用本地的组，以及用户明确选择“在云端删除”的组）、冲突/本地删除待处理组、无需上传组（相同、云端领先或已有有效保留云端授权）。不同内容的冲突可选择保留云端或采用本地整组；不按机器时钟、非空字段或逐字段拼接自动择优。采用本地的提交选择绑定本次 L/C/B 摘要及预期云端版本；内容变化后重新预检。“保留云端”则持久化为逐组下载授权，绑定 project_id、ledger_id、group_kind、group_key、该组当时 L/C/B 的完整内容快照（含存在性、全部业务字段、审计时间及有序列表，B 显式区分无基线与已确认不存在）、各快照摘要及选择版本。它只授权以该组云端状态覆盖该组本地状态，含删除；不是整个账本的放弃授权。记录所见 cloud_revision 用于追溯，其他组提交造成 revision 增长不单独使该授权失效；push 和 pull 都必须逐组重验授权：先用摘要校验保存的原始快照完整性，再将当前 L/C/B 分别与授权时保存的对应快照比较；业务字段按约定浮点容差比较，存在性、无基线状态、身份、空值、明细存在性及列表顺序严格比较，created_at/updated_at 另行严格比较。容差内的浮点差异不使授权失效；任一审计时间变化则授权失效，即使业务相等。授权绑定校验与忽略审计时间的三方业务比较是两套判断，不得混用，也不得对当前内容重新哈希后以摘要相等代替重验。快照损坏或绑定校验不通过时，该组授权失效，须重新选择。已有有效授权的组在下次 push 中优先归入无需上传，报告“已授权保留云端，待下载”，不得再次列为尚未选择的冲突或自动上传；push 不因此改本地或推进该组基线。
- “无需上传”必须保留三种独立分类，不能共用基线收尾逻辑：内容相同的组经完整快照确认且本地未变后，可确认新共同基线；云端领先待下载的组保留原基线；已授权保留云端待下载的组只报告待下载，保留原基线，不因授权有效而视为内容相同或已完成。后两类无基线时也不新建基线，须等待下载成功后再推进。
- 本地删除待处理的选择必须落为以下动作：选择“把云端恢复到本地”，保存同一类逐组下载授权（action=keep_cloud），其中授权时的 local_payload 明确为不存在，仍保存完整 C/B 及对应摘要，并沿用上述授权重验规则；授权有效时，下次 push 报告“已授权保留云端，待下载”，不再列为“本地删除待处理”，不改本地或推进基线，待全量 pull 成功后恢复并消费授权。选择“在云端删除”，将该组作为显式云端删除加入可提交集合，提交内容明确为该组存在性不存在，并绑定本次 L/C/B 摘要及预期云端版本；内容或版本变化后重新预检。这是用户明确授权的删除，不是自动合并；按组删除云端业务数据及其关联记录，复盘与事件仍互不级联。该删除与其他可提交组共用一次同步事务 RPC，删除历史、revision 和包含不存在状态的提交结果同事务更新，集合内任一失败全部回滚；确定成功后按不存在状态推进该组基线，结果未知则沿用待核验和原操作恢复规则。
- **无冲突组先同步**：可提交集合通过一次专用同步事务 RPC 原子提交，冲突组完全不写；存在冲突不阻止第二台独有日期等可提交数据。提交集合内任一约束错误或预期云端版本变化，整个集合回滚，禁止数据库内逐组吞错。集合为空时不发写 RPC。大请求超限整体失败，不静默拆批。
- “采用本地”采用的是本地整组状态，包含存在性：L 存在时保留源 created_at/updated_at 并写入整组；L 不存在时（包括本地已删、云端相对基线也已修改的冲突）视为用户明确授权删除，走与“在云端删除”相同的显式删除提交路径，加入可提交集合，提交存在性为不存在，不写入业务行、不构造源时间戳。两条删除入口均绑定本次 L/C/B 摘要及预期云端版本，沿用同一事务、历史、revision、结果和未知结果恢复规则；确定成功后，基线记为已确认不存在。冲突报告在 L 不存在时必须说明选择“采用本地”将删除云端该组。
- 对于提交状态为存在的组，新增、只有本地改动及用户明确选择本地的组保留源 created_at/updated_at；提交状态为不存在的组执行显式删除。两者均不调用日常写 RPC。服务端校验 schema、操作摘要、预期版本、选择的组身份及关联约束后执行对应操作；预检显示“可提交”不代表已经成功。
- 结果分别列出已提交、相同跳过、云端领先待下载、已授权保留云端待下载、冲突、本地删除待处理及失败集合。仅在全部组完成且没有待下载、冲突或本地删除待处理项时为 completed；云端领先待下载和已授权保留云端待下载都属于未完成项，不能计入已确认成功/相同组。已有确认成功/相同组但仍有待处理项为 partial；只有待处理项为 needs_resolution；报告必须按处理方式分为三类：①待下载（云端领先或已授权保留云端），说明待下载原因，已有有效授权不要求重新选择；②尚未选择的冲突，列出本地与云端两边内容，等待用户选择“保留云端”或“采用本地”；③本地删除待处理，等待用户选择“把云端恢复到本地”或“在云端删除”。不得把后两类报告成待下载；提交失败或结果未知分别报告 failed/unknown，不能宣称整次成功。冲突清单不是“在途待核验记录”，云端提交及本地基线落盘确认后关闭操作记录，未解决冲突留作报告，不永久锁住其他写入。
- 本地缺少记录不自动删除云端，需要显式云端删除。删除/方向替换与组历史在同一事务更新；有基线且仅云端删除时接受云端领先，不把旧本地未改数据当成待恢复；两边修改不同或无基线命中删除历史才报告冲突。明确恢复仍须用户选择。

### 7.2 同步元数据、并发和未知结果

增加基础设施对象：账本单调 revision、组级删除/变更历史、同步 operation_id/请求摘要/提交结果；本地记录来源项目、本地账本标识、逐组共同基线及同步操作状态；上传和下载都可能推进基线，不再只记录最后下载状态。基础设施字段及职责见[数据库设计第 7 节](数据库设计.md#7-待实现同步基础设施)。全新账本由显式迁移初始化空历史；从旧库升级时没有历史的云端缺行不视为已知删除，首次两机接入必须通过差异报告确认，不能伪造过往删除记录。元数据属于同步协议，不进入 summary/ladder，不用业务时间戳当版本。

所有七类日常云端写 RPC、同步提交均在事务内通过同一账本元数据锁串行变更并更新 revision；删除及方向替换同时更新历史。同步提交对预检版本进行比较，变化则拒绝并重新预检；不宣称替代跨机器的操作协调。备份/恢复须包含这些基础设施对象及相应权限。

发送前在固定本机状态目录内持久化 operation_id、摘要、计划及每个提交组的完整源内容（含存在性、时间和有序列表）；与方向替换共用 write.lock 和未关闭记录闸门。云端同一 operation_id 与同一摘要重复提交只返回已存结果，不重复写；同 ID 不同摘要拒绝。业务写入、revision 及成功结果同事务提交。超时后先查操作结果，未找到也不能推断回滚；允许按同 ID/同摘要受控重试，数据库唯一约束及事务锁须处理原请求仍在途的情况。操作记录未关闭前禁止新的云端写入、另一次同步及会改变本地源的写入。同 ID 重试须先核对已存结果再检查预期版本；不能因该操作自身已提升 revision 而拒绝返回原结果。

共同基线绑定 (project_id, ledger_id, group_kind, group_key)，保存已确认共同状态的完整组内容、存在性和对应 cloud_revision，不只存时间或无法还原的摘要。全量 pull 成功时五表、全部基线、完整快照覆盖标记及下载结果在同一个 SQLite 事务提交；覆盖标记使从未存在的组可明确视为基线不存在。首次未覆盖的组仍为无基线。

push 得到确定成功结果后，只为已提交组以及经完整快照确认业务相同且本地未变的组推进基线；没有可提交组时无需云端写 RPC，仍可在本地事务中确认相同组基线，但须先核验本地内容未变；未提交、冲突、失败、云端领先待下载及已授权保留云端待下载组保留原基线。不得用一个全局“最后同步版本”覆盖全部组。服务器成功但本地基线写入失败时保持操作未关闭；恢复时按 operation_id 取原提交结果，以发送前持久化的完整源组内容推进已提交组基线，而不是用恢复时可能已修改的本地内容伪造共同状态。云端提交结果必须保存各已提交组的完整实际提交内容并与业务同事务提交，可在本机源快照丢失/损坏时按原 operation_id 恢复；哈希只能校验，不能替代完整内容。不读取当前业务行反推旧提交状态；本机完整源内容与云端 result_payload 都在时，必须核对同一操作的组集合、存在性、业务字段（浮点按约定容差）、审计时间及列表顺序；任一不一致即停止，不推进任何基线，保留待核验状态，不能挑选其中一份继续。两处证据都不完整时同样停止并保留待核验状态。SQLite 中基线和本地操作结果在同一事务持久化，之后才关闭外部待核验记录；中断重做本地收尾必须幂等。本机状态目录固定 ~/.marketreview/supabase-state/，不跟随 --db、MARKETREVIEW_HOME 或项目改变；版本化 JSON 保存待核验操作。使用固定 write.lock 的 fcntl.flock 排他锁，检查、前像/计划落盘、发送及必要结果落盘在同次锁持有内；文件使用原子替换和 fsync 持久化，失败不发送。关闭、重新打开及重发之间不释放锁。测试只可通过内部依赖注入使用临时目录，不提供生产 CLI/环境变量覆盖入口，测试绝不访问真实状态目录。

### 7.3 云端全量下载到本地

允许目标为当前日常 SQLite（包括默认路径及 MARKETREVIEW_HOME）。这是把权威云端下载到一份本地副本，不是要求两台日常库互相拉齐。禁止目标为备份目录及已登记的迁移前快照，检查规范化路径、符号链接和同文件别名。`partial` 或待下载不是「云端没有这份上传」。

下载按第 7.1 节 L/C/B 分类，而不是只要 L≠C 就拒绝。有基线且只有云端变化（含删除）可以直接下载；没有基线且仅云端新增也可下载。只有本地改变、两边冲突、本地删除待处理或首次本地独有数据，且没有对应有效逐组“保留云端”授权时，才阻止全量 pull。先列出全部阻止组，建议上传或逐组解决；push 已保存的有效授权在 pull 中直接使用，不要求对同一内容再授权。任何新增放弃选择也必须逐组记录，可一次确认明确列出的多组，但不能使用覆盖未列出组的全局放弃开关。只要仍有一个未授权的阻止组，整次 pull 不写业务、不推进基线、不消费任何授权；保留其他组的授权等待后续使用。pull 仍是五表全量原子更新，不做部分下载；初次两机接入应先分别处理原库内容，再下载覆盖。

实现采用 SQLite 事务更新五表，不直接替换 .sqlite3 文件、不手工删除 -wal/-shm。取得本机目标锁并暂停其他本地使用者，使用 SQLite 一致备份接口创建新备份并校验；备份失败不修改目标。验证完整云端快照后，在一个 SQLite 写事务中替换五表数据、保存全部共同基线、完整覆盖标记及下载结果，并将本次使用的逐组授权标为已消费，事务内核对行数、内容、时间、顺序及外键后提交。上述基线推进和授权消费仅在本地业务内容已与本次云端快照一致且事务提交时生效；事务失败全部回滚，授权仍可按内容重验后使用。保留现有 schema 和必要本地元数据；无论 backend 默认值如何都不改其配置。

SQLite 自己管理 WAL/SHM，失败回滚保持原有逻辑数据，附属文件字节不承诺完全不变；这取代旧的“三文件完全不动+文件替换”方案。取得写事务后重验本地与预检状态一致，发现并发修改即回滚；锁失败或目标被占用则报错，不强制关闭其他程序。中断后通过原子提交状态与下载操作标识判定是否完成，不能盲目重新覆盖。备份、云端项目、版本、下载 operation_id 和结果需可追溯。
