## 云端方案状态

权威账本是 Supabase PostgreSQL，详见 [Supabase 云端后端设计](Supabase云端后端设计.md)。本地 `market_review.sqlite3` 是可选副本，不是与云端对等的第二本账。2026-10-03 起未写 `backend` 时日常默认是 Supabase（`CLOUD_DEFAULT_ENABLED=True`）；配置文件里的 `backend=sqlite` 仍会盖过该默认值。第 1–6 节描述业务表在本地副本上的实现，第 7 节是上传/下载用的本地元数据加云端 revision、历史和操作结果（`sql/migrations/0003_marketreview_v1_sync.sql`，同步语句超时见 `0004_sync_statement_timeout.sql`）。#10 未关闭。旧版「默认打开 SQLite 文件」的路径说明只适用于显式 `--backend sqlite`。

## 1. 分层

| 位置 | 职责 |

约束：

- 公共字段使用 `snake_case`。
- 数据库使用 SQLite STRICT 表。
- Skill 与外部应用都通过 `scripts/cli.py` 读写，不直接 import 包操作 SQLite（测试除外）。
- CLI 不提供复杂的外部采集编排接口。

## 2. 数据库定位

现行 SQLite 默认文件路径（不是新版本默认后端）：

```text
~/.marketreview/market_review.sqlite3
```

路径优先级：`CLI --db` > `MARKETREVIEW_HOME/market_review.sqlite3` > 默认路径。

- Skill 安装目录不保存用户数据。
- 多个 Agent 可共享同一份用户数据。
- 打开已有数据库时执行 `CREATE TABLE IF NOT EXISTS` 补齐新表，不改写已有用户数据。
- 涉及已有列变化时必须使用显式 schema migration，并保留已有数据。

连接初始化必须执行 `PRAGMA journal_mode=WAL`、`PRAGMA busy_timeout=5000` 和 `PRAGMA foreign_keys=ON`，并读取实际值确认。文件数据库的 `journal_mode` 必须为 `wal`；内存数据库允许 `memory`。若连接已在事务中导致 PRAGMA 无效，必须拒绝初始化。

## 3. 核心数据表

| 数据表 | 用途 |
| --- | --- |
| `daily_market_review` | 每个交易日一条总体复盘；只保存原子指标 |
| `daily_price_limit_event` | 一只股票在一个交易日触及一个方向的涨跌停价时一条记录 |
| `daily_price_limit_event_detail` | 与一条触板事件一对一的可空明细 |
| `daily_price_limit_event_sector` | 事件的有序、多值所属板块 |
| `daily_price_limit_event_reason` | 事件的有序、多值涨停原因 |

`daily_price_limit_event` 使用 `(trade_date, market, code, direction)` 作为主键。涨跌停事实独立于总体复盘：删除 `daily_market_review` 不删除同日事件。三张明细表以外键级联到事件；删除事件时级联删除明细。

入库身份使用 `(market, code)`：`market` 为小写 `sh | sz | bj`，`code` 为保留前导零的 6 位字符串。不维护证券主表。

`daily_market_review` 只保存各指数收盘与前收盘、各市场融资余额和成交额等原子字段。有效涨停、炸板、连板汇总、合计和涨跌幅均不保存在该表中。

`is_leader` 在 SQLite 中用 `INTEGER` 的 `1` / `0` / `NULL` 存储；公共返回值转换为 Python `bool | None`。

## 4. 表结构

```sql
CREATE TABLE IF NOT EXISTS daily_market_review (
    trade_date TEXT NOT NULL PRIMARY KEY,
    pullback_count INTEGER,
    median_change_pct REAL,
    advancing_count INTEGER,
    declining_count INTEGER,
    margin_balance_sh REAL,
    margin_balance_sz REAL,
    margin_balance_bj REAL,
    sh_index_close REAL,
    sh_index_prev_close REAL,
    sz_index_close REAL,
    sz_index_prev_close REAL,
    cy_index_close REAL,
    cy_index_prev_close REAL,
    turnover_amount_sh REAL,
    turnover_amount_sz REAL,
    turnover_amount_cy REAL,
    turnover_amount_bj REAL,
    total_market_cap REAL,
    float_market_cap REAL,
    pe_sh REAL,
    pe_sz REAL,
    pe_cy REAL,
    pe_all REAL,
    avg_stock_price REAL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
) STRICT;

CREATE TABLE IF NOT EXISTS daily_price_limit_event (
    trade_date TEXT NOT NULL,
    market TEXT NOT NULL,
    code TEXT NOT NULL,
    name TEXT NOT NULL,
    direction TEXT NOT NULL,
    closed_at_limit INTEGER NOT NULL,
    limit_rate_bp INTEGER NOT NULL,
    streak_height INTEGER NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    PRIMARY KEY (trade_date, market, code, direction)
) STRICT;

CREATE TABLE IF NOT EXISTS daily_price_limit_event_detail (
    trade_date TEXT NOT NULL,
    market TEXT NOT NULL,
    code TEXT NOT NULL,
    direction TEXT NOT NULL,
    previous_turnover_amount REAL,
    auction_amount REAL,
    previous_close REAL,
    open_price REAL,
    turnover_amount REAL,
    turnover_rate REAL,
    is_leader INTEGER,
    note TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    PRIMARY KEY (trade_date, market, code, direction),
    FOREIGN KEY (trade_date, market, code, direction)
        REFERENCES daily_price_limit_event (trade_date, market, code, direction)
        ON DELETE CASCADE
) STRICT;

CREATE TABLE IF NOT EXISTS daily_price_limit_event_sector (
    trade_date TEXT NOT NULL,
    market TEXT NOT NULL,
    code TEXT NOT NULL,
    direction TEXT NOT NULL,
    position INTEGER NOT NULL,
    value TEXT NOT NULL,
    PRIMARY KEY (trade_date, market, code, direction, position),
    UNIQUE (trade_date, market, code, direction, value),
    FOREIGN KEY (trade_date, market, code, direction)
        REFERENCES daily_price_limit_event (trade_date, market, code, direction)
        ON DELETE CASCADE
) STRICT;

CREATE TABLE IF NOT EXISTS daily_price_limit_event_reason (
    trade_date TEXT NOT NULL,
    market TEXT NOT NULL,
    code TEXT NOT NULL,
    direction TEXT NOT NULL,
    position INTEGER NOT NULL,
    value TEXT NOT NULL,
    PRIMARY KEY (trade_date, market, code, direction, position),
    UNIQUE (trade_date, market, code, direction, value),
    FOREIGN KEY (trade_date, market, code, direction)
        REFERENCES daily_price_limit_event (trade_date, market, code, direction)
        ON DELETE CASCADE
) STRICT;
```

多值表的 `position` 从 `0` 开始连续编号，保留输入顺序。不把外部来源序号直接入库。

## 5. 读写能力

数据层提供：

- 新增或 patch 指定交易日的总体复盘原子字段。
- 查询单个交易日或日期范围的原子字段。
- 删除指定交易日的总体复盘；涨跌停事件作为共享事实独立保留。
- 保存、更新和删除涨跌停事件；空事件列表为 no-op。
- 在同一事务中按旧方向删除并写入新方向事件（`replace_price_limit_event_direction`），同时迁移明细标量和 `sectors`；改为 `down` 时不迁移 `limit_up_reasons`。
- patch、查询事件明细及其多值板块、涨停原因；父事件不存在时整批失败。
- 读取事件与明细后生成单日梯队和炸板、跌停辅助名单。
- 组合查询单日的原子字段和事件；总体复盘或涨跌停事件任一存在即返回，二者都不存在才视为无数据。

批量写入使用普通事务，避免数据库故障造成半批写入，不代表数据库确认内容正确。

现行日常 repository 除原子方向替换接口外，不定义 `direction_replace`、`item_patch` 等额外操作模型。

## 6. 技术验收

1. schema 更新不得损坏已有用户数据。V1 数据库打开后自动增加 V2 三张扩展表，原事件与复盘行不变。
2. 测试覆盖新建数据库、仅含 V1 表的已有数据库，以及活动事务中 WAL / foreign keys 未能开启时拒绝初始化。
3. `daily_price_limit_event` 使用日期、市场、代码和方向作为唯一键；方向变更必须通过 `replace_price_limit_event_direction` 在同一事务中完成，不能只改 `direction`，也不能依赖非事务的先删后写。
4. 批量保存事件或明细时，任一条失败整批回滚。
5. 删除事件级联删除 detail、sector 和 reason。
6. 字段级 patch 正确区分未提交、`null`、`0` 和 `false`；多值列表区分未提交、非空替换和 `[]` 清空。
7. 父事件不存在时拒绝写入明细。
8. `get` 保持 V1 的 `review` / `events` / `summary` / `missing_fields`，并新增 `ladder`。
9. `2026-08-21` 已由仓库沪深交易日历确认为已收盘交易日，前一交易日固定为 `2026-08-20`。黄金 fixture 至少覆盖连续多个交易日的涨停、当日跌停、首板、连板、炸板、打开跌停、收盘跌停、用户提供高度和缺省计算高度，以及展示统计预期。梯队股票总数必须与同一 fixture 的有效涨停数一致。
10. 持久化验收覆盖新增、更新、查询、删除和数据库故障时不会留下半批数据；业务内容正确性由 Skill 和用户负责。
11. repository 不根据股票名称推断 ST，也不复核证券宇宙过滤结果。


## 7. 同步基础设施

本节规定把本地副本上传到权威云端、或把云端完整下载到一份本地副本时使用的记录。它不要求两台机器的日常库保持一致。物理表名和 SQL 类型以版本化迁移为准。业务行为及三方比较以[云端后端设计第 7 节](Supabase云端后端设计.md#71-同步协议与合并规则)为准。本地实现见 `scripts/marketreview/sync_ledger.py`，云端迁移见 `sql/migrations/0003_marketreview_v1_sync.sql`。

### 7.1 身份与比较单位

五张业务表的主键和外键不变。同步 group_key 有两种：review 使用 trade_date；event 使用 trade_date、market、code，组内容包含当日该证券全部方向事件及关联明细和列表。此分组用于识别方向替换，不是新的事件主键；复盘与事件仍无级联。

本地 ledger_id 是账本身份，路径移动不改变它；复制给另一机器独立写入时须显式建立新身份并复制/验证对应基线，不能让两个可独立变化的账本共享未完成操作。本地所有基线按 project_id 隔离。下列 group_payload 是同步元数据快照，业务数据仍存五表，不改成每日 JSON。

### 7.2 云端记录

| 逻辑对象 | 必需字段与约束 |
| --- | --- |
| 账本版本 | ledger_key（单账本唯一）、schema_version、revision（单调整数）；所有业务写事务共用锁，数据变更与版本一起提交 |
| 组变更历史 | group_kind、group_key、revision、change_kind（更新/删除/方向替换/同步）、before_exists、after_exists、operation_id（可空）；组和 revision 形成唯一事件；删除历史不能随业务行级联消失 |
| 同步提交结果 | operation_id（唯一）、project_id、ledger_id、request_digest、expected_revision、committed_revision、result_version、result_payload（每个已提交组的完整实际提交内容，包含存在性、全部业务字段、审计时间和有序列表；不得仅保存哈希或源摘要引用）；成功结果和业务同事务提交。同 ID 不同摘要拒绝 |

历史和结果须随备份恢复，第一版不自动清理；以后清理必须保留仍可能被旧本地基线或待核验操作引用的证据。函数权限同业务表，普通匿名及 authenticated 不可访问。已有业务表升级只能记录升级后的历史，不能推断升级前的删除。

### 7.3 本地 SQLite 同步记录

| 逻辑对象 | 必需字段与约束 |
| --- | --- |
| 账本身份 | ledger_id、metadata_schema_version；独立于文件路径 |
| 逐组共同基线 | project_id、ledger_id、group_kind、group_key（联合唯一）、exists、group_payload（完整确认状态含时间及列表）、cloud_revision、confirmed_operation_id |
| 全量覆盖标记 | project_id、ledger_id、snapshot_revision、pull_operation_id；只在成功全量下载时更新，结合组基线区分“已确认不存在”与“未建立基线” |
| 逐组下载授权 | project_id、ledger_id、group_kind、group_key、decision_id、decision_version、action=keep_cloud、local_payload、cloud_payload、baseline_payload（保存授权时 L/C/B 完整内容，含存在性、全部业务字段、审计时间及有序列表；B 显式区分无基线与已确认不存在）、local_digest、cloud_digest、baseline_digest（仅校验对应原始快照完整性）、observed_cloud_revision、state（active/consumed/invalid）；授权不覆盖其他组，与基线独立保存 |
| 本地同步结果 | operation_id（唯一）、project_id、ledger_id、kind、request_digest、state、result_payload、backup_path（可空）；与相关基线更新同 SQLite 事务 |

每组独立选择比较规则：有可信基线使用三方比较，无基线使用首次接入规则；无基线仅云端存在的组，push 归无需上传/待下载，不建基线、不阻止其他组提交。所有 L=B、C=B、L=C 判断都使用忽略 created_at/updated_at 的业务相等，不比较 group_payload 整包或直接比较哈希。

“无需上传”分为内容相同、云端领先待下载、已授权保留云端待下载三类。只有内容相同且经完整快照确认、本地未变的组可确认新共同基线；后两类在 push 中只报告待下载，保留原基线，无基线时也不新建，等待下载成功后再推进。有效授权不等于内容相同，也不代表该组已完成。

冲突判断不按审计时间取新值；业务比较使用既定浮点容差和严格结构比较。相同业务但审计时间不同时保留云端时间为共同基线，push 不为此改写本地业务；之后比较仍忽略审计时间，pull 会严格复制云端审计时间。

基线是已确认共同状态，不是最近看见的云端状态。成功 push 只推进已提交/确认相同的组；云端领先、冲突、失败或未提交组不推进。全量 pull 将五表、基线、覆盖标记及结果一起提交。云端提交成功、本地收尾失败不回滚云端，依原 operation_id 恢复本地基线；不能重发为新操作。发送前待核验记录必须持久化每个提交组完整源内容；云端结果也保存完整实际提交内容。恢复使用这两处原始内容并校验摘要，不能依赖已变化的本地/云端当前行；哈希无法还原原内容。本机完整源内容与云端 result_payload 都在时，核对同一操作的组集合、存在性、业务字段（浮点按约定容差）、审计时间及列表顺序；任一不一致即停止，不推进任何基线并保留待核验，禁止任选一份继续。比对前须将 JSON 传输后的数值恢复为现行 Python 类型（`double precision` 字段为 `float`）：PostgreSQL `jsonb` 常把整值浮点编成 JSON 整数，不能直接用未恢复的 int 与本机 float 做严格类型比较。本机源快照丢失/损坏时可按原 operation_id 的完整云端提交结果恢复；两处证据都不完整时停止并保留待核验。

### 7.4 事务及验收边界

无冲突上传集合一次事务提交，冲突组排除在外；集合内失败全回滚，与“存在冲突时允许其他组先成功”不矛盾。报告须区分 completed、partial、needs_resolution、failed、unknown。云端领先待下载和已授权保留云端待下载均计入未完成项：与确认成功/相同组混合时报 partial，只有待处理项时报 needs_resolution。报告必须按处理方式分为三类：①待下载（云端领先或已授权保留云端），说明待下载原因，已有有效授权不要求重新选择；②尚未选择的冲突，列出本地与云端两边内容，等待用户选择“保留云端”或“采用本地”；③本地删除待处理，等待用户选择“把云端恢复到本地”或“在云端删除”。不得把后两类报告成待下载；存在任一待下载、冲突或本地删除待处理项时不得报 completed。未解决冲突不等于请求在途，确认提交结果及本地基线后可关闭操作闸门。

可提交集合包含自动合并、用户明确选择“采用本地”的组及用户明确选择“在云端删除”的组。本地删除待处理的选择必须落为以下动作：选择“把云端恢复到本地”，保存同一类逐组下载授权（action=keep_cloud），其中授权时的 local_payload 明确为不存在，仍保存完整 C/B 及对应摘要，并沿用本节逐组下载授权重验规则；授权有效时，下次 push 报告“已授权保留云端，待下载”，不再列为“本地删除待处理”，不改本地或推进基线，待全量 pull 成功后恢复并消费授权。选择“在云端删除”，将该组作为显式云端删除加入可提交集合，提交内容明确为该组存在性不存在，并绑定本次 L/C/B 摘要及预期云端版本；内容或版本变化后重新预检。这是用户明确授权的删除，不是自动合并；按组删除云端业务数据及其关联记录，复盘与事件仍互不级联。该删除与其他可提交组共用一次同步事务 RPC，删除历史、revision 和包含不存在状态的提交结果同事务更新，集合内任一失败全部回滚；确定成功后按不存在状态推进该组基线，结果未知则沿用待核验和原操作恢复规则。

“采用本地”采用的是本地整组状态，包含存在性：L 存在时保留源 created_at/updated_at 并写入整组；L 不存在时（包括本地已删、云端相对基线也已修改的冲突）视为用户明确授权删除，走与“在云端删除”相同的显式删除提交路径，加入可提交集合，提交存在性为不存在，不写入业务行、不构造源时间戳。两条删除入口均绑定本次 L/C/B 摘要及预期云端版本，沿用同一事务、历史、revision、结果和未知结果恢复规则；确定成功后，基线记为已确认不存在。冲突报告在 L 不存在时必须说明选择“采用本地”将删除云端该组。

本地删除不自动上传为云端删除；只有云端变化时 pull 可采用云端状态，两边不同改动才冲突。无基线首次接入保守比较，不把缺基线当作历史空值。日常 SQLite 写入改变业务数据但不推进共同基线。

“保留云端”是逐组下载授权，不在 push 中改本地或提前推进基线。push 和 pull 均先用摘要校验授权时保存的 L/C/B 原始快照完整性，再将当前对应内容与快照重验：业务字段按 math.isclose(rel_tol=1e-12, abs_tol=1e-9) 的浮点容差比较，存在性、无基线状态、身份、空值、明细存在性和列表顺序严格比较，审计时间另行严格比较。容差内浮点差异不使授权失效，审计时间变化则使授权失效；这与忽略审计时间的三方业务相等判断必须分开实现。不得以当前内容重新哈希后的摘要相等代替重验；原快照损坏或绑定校验失败则授权失效，须重新选择。无关组更新导致的总 revision 变化不单独使授权失效。已有有效授权的组下次 push 优先归入无需上传/已授权保留云端待下载，不再当成未选择的冲突或自动上传。有效授权只解除对应组阻止，任何其他未授权本地修改/删除/冲突仍阻止全量 pull；不提供全局放弃开关。事务未执行或失败时不消费授权；成功时先达到本地与云端快照业务一致，再与五表/基线同事务标记授权已消费。

下载先备份，在 SQLite 单写事务更新五表及同步记录，由 SQLite 管理 WAL/SHM，不直接替换文件。测试覆盖本地删除且云端相对基线也修改时仍归冲突，选择“采用本地”后按显式删除提交、不写业务行，成功后基线为已确认不存在，并验证版本变化拒绝、整批回滚及未知结果恢复；本地删除选择“把云端恢复到本地”后保存 L 不存在的 keep_cloud 授权、再次 push 改报已授权待下载且在其他阻止项清除后 pull 可恢复；选择“在云端删除”后进入可提交集合，以不存在状态提交并更新历史及基线，不插入业务行，版本变化拒绝且集合内失败整批回滚；授权 L/C/B 完整快照及摘要损坏、容差内差异保持授权有效、审计时间变化使授权失效但不误报业务冲突、有效授权再次 push 只待下载、三类无需上传的基线收尾区别及两类待下载不得计为 completed（仅待下载为 needs_resolution，与成功/相同组混合为 partial）、仅有未决冲突或本地删除待处理时 needs_resolution 分别提供冲突选项与删除处理选项而非待下载提示、三类待处理项混合时分别报告所需动作、两份恢复证据不一致时停止并保留待核验、三方比较、首次接入、部分提交、基线恢复、删除/方向替换、云端版本变化、WAL 及备份恢复；现行第 6 节日常接口验收继续适用。
