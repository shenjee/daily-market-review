# 每日市场复盘 Skill PRD

- 文档类型：现行产品与数据规范
- Skill 名称：`daily-market-review`
- 所属项目：daily-market-review
- 适用范围：总体复盘、每日涨跌停事件、每日梯队与情绪周期图
- 指标附录：[《每日市场复盘 Skill PRD》附录：指标说明与统计口径](资本市场复盘指标说明与统计口径.md)

## 1. 产品目标

每日市场复盘用于记录、修正和展示指定已收盘交易日的资本市场数据，形成口径稳定的日度复盘账本。

数据库是长期积累的数据资产，不只服务于 Skill，也必须能够直接支持 Stock Pilot 应用。

本文档只规定 `daily-market-review`；其他 Skill 的范围与触发词不在本文档处理。

## 2. 职责边界

| 层 | 职责 |
| --- | --- |
| `scripts/marketreview/` | 数据表结构、SQLite 持久化、读取侧统计，以及交易日历和最小行情能力 |
| `scripts/cli.py` | JSON CLI 入口；写入路径执行业务校验后再落库 |
| `daily-market-review` Skill | 理解用户请求，通过 API、网页、图片或用户文字取得数据，调用 CLI 写入；读取后格式化展示 |

约束：

- Skill 通过 `scripts/cli.py` 读写，不直接 import 包，也不直接操作 SQLite。
- 写入路径在 CLI 中校验交易日期、市场、代码、方向和涨跌幅限制；repository 仍只做结构性持久化，不复核行情事实是否正确。
- 行情类指数日 K 由内置 `scripts/marketreview/sources/tencent.py` 提供；其余数据由 Agent 通过腾讯、东方财富、网页、图片、用户输入或其他可用来源取得。
- CLI 将调用方提交的数据视为待保存内容，按原样存取，不重复判断市场事实是否正确，也不改写提交的数值。SQLite 使用 STRICT 表承担字段类型、可空性、行身份唯一性和事务安全等结构性职责。
- 数据可能录错；用户在查看时发现问题后，可以让 Skill 修订或覆盖。数据库不承担事实核验职责。
- 腾讯指数 K 线里的 `amount` 不等同于交易所全市场成交额，不作为市场成交额自动写入。

## 3. 功能范围

### 3.1 总体复盘

总体复盘包含指定交易日的以下数据：

| 类别 | 指标 |
| --- | --- |
| 涨跌停 | 有效涨停、20% 涨停、打开跌停、收盘跌停、涨停炸板、炸板率 |
| 市场宽度 | 回头波数、中位数涨跌幅、上涨家数、下跌家数、涨跌停比 |
| 连板 | 首板数、连板数、连板率、最高板、最高板代表、按实际高度动态分组的数量 |
| 两融 | 上海融资余额、深圳融资余额、北京融资余额、融资余额合计 |
| 指数 | 上证指数、深证成指、创业板指的点位、涨跌点数和涨跌幅 |
| 成交额 | 上海、深圳、创业板、北京及合计成交额；创业板单独展示但已包含在深圳成交额中 |
| 市场规模与估值 | 总市值、流通市值、上海 PE、深圳 PE、创业板 PE、全市场 PE |
| 平均股价 | 平均股价 |

指标及展示统一使用成交额。

两融类别包含上海、深圳、北京融资余额；“补齐两融”处理这三项。存储字段为 `margin_balance_sh` / `margin_balance_sz` / `margin_balance_bj`。

市场 PE 不由系统计算，直接记录同花顺在指定交易日展示的市盈率，不使用各市场 PE 进行加权或算术平均。上海 PE 对应同花顺 `000001`，深圳 PE 对应同花顺 `399001`，创业板 PE 对应同花顺 `399006`。以 2026-08-21 为例，`000001` 市盈率为 `17.00`，`399001` 市盈率为 `30.67`。系统直接保存数值，不自行解释为 TTM 或静态 PE。

指数点位与分市场 PE 必须按下列规范代码取数。

| 指标 | 规范代码 | 名称 |
| --- | --- | --- |
| 上证指数、上海 PE | `000001`（规范标识 `sh000001`） | 上证指数 |
| 深证成指、深圳 PE | `399001`（规范标识 `sz399001`） | 深证成指 |
| 创业板指、创业板 PE | `399006`（规范标识 `sz399006`） | 创业板指 |

平均股价不由系统根据个股价格计算。同花顺对应代码为 `830000`，申万宏源对应代码为 `880003`。该字段由 Skill 取得或由用户提供，未取得时留空。

市场宽度覆盖上海、深圳和北京市场，证券软件统计范围包含停牌和无成交股票。上涨家数、下跌家数、中位数涨跌幅和回头波数直接记录证券软件展示的数值，由 Skill 取得或由用户提供；未取得时留空。回头波定义为 `最高价 ÷ 收盘价 - 1 > 10%`，严格使用 `>`；系统不遍历全市场重新计算。

系统只处理收盘后的日度数据，不处理午间涨停、午间成交额、开盘成交额和开盘情绪。

每日涨跌停事件按交易日、股票和方向保存，并记录收盘是否仍处于对应涨跌停价格。数据库不判断某日名单是否完整，也不判断事件内容是否符合真实行情；未保存的事件按数据库中不存在处理。展示时，Skill 根据已保存事件统计有效涨停、涨停炸板、打开跌停、收盘跌停、首板和连板等指标。

### 3.2 每日梯队

每条涨跌停事件都直接保存 `streak_height`，表示该股票在记录当天的连续涨停高度。用户提供了连板数时，Skill 采用用户提供的值；用户未提供时，有效涨停按数据库中的前一交易日事件计算，前一交易日同股有效涨停则在其已保存高度上加一，否则为首板 `1`。涨停炸板和跌停事件写 `0`。Skill 计算完成后写入，数据库只保存最终值，不回溯、递推或校验。不另建重复的连板分布表或日度聚合表。

每日梯队不是另一份股票名单。Skill 读取现有 `daily_price_limit_event`，筛选 `direction=up and closed_at_limit=true and streak_height>=1` 的有效涨停事件，并按实际高度从高到低动态分组。首板属于梯队；高度不限制在 11 板，也不生成固定板高字段。

每条事件包含以下可空梯队字段：

- 多值所属板块 `sectors`；
- 多值涨停原因 `limit_up_reasons`（仅 `direction=up`）；
- 昨日成交额、开盘竞价额、昨日收盘价、今日开盘价、当日成交额和换手率；
- 是否龙头和备注。

竞价占比和开盘涨幅由原始字段读取后计算，不重复入库。系统不保存分时序列、日 K 序列、走势图图片或行情接口原始响应。

涨停炸板、打开跌停和收盘跌停不属于梯队，但保留在同一份每日涨跌停事件中，作为独立名单展示。事件明细不得改变核心触板事实或总体复盘统计。

### 3.3 情绪周期图

根据已有总体复盘和每日涨跌停事件生成跨交易日视图，主要展示每日最高连板数、最高板代表、有效涨停数量、连板数量、涨停炸板、打开跌停、收盘跌停和各板高度数量。

情绪周期图是展示视图，不单独保存重复的日度聚合结果。

总体复盘表如需紧凑展示，Skill 可以将 11 板及以上合并为 `11板+`；展示统计按实际高度动态分组，不生成 `board_1` 至 `board_11_plus` 等固定字段。情绪周期图按每日实际高度分组。

## 4. 数据获取与指标出数合同

每个指标必须属于以下三类之一，并作为验收依据。第 4 节是指标出数承诺，第 5 节是本次请求的取数模式；「自动获取」不等于「自动整理」。

### 4.1 Skill 自动获取

固定自动获取项仅包括：

- 上证指数日 K（规范标识 `sh000001`，代码 `000001`）
- 深证成指日 K（规范标识 `sz399001`，代码 `399001`）
- 创业板指日 K（规范标识 `sz399006`，代码 `399006`）

Skill 通过内置腾讯日 K 取得三只指数当日收盘和前收盘，再经 `save-review` 写入 `daily_market_review` 原子字段。只提交成功取得且校验通过的完整指数点位对；获取失败的指数不进入本次 patch，因此已有记录保持原值，新记录对应字段留空。不得用其他日期数据顶替。请求范围包含哪些指数字段且未指定来源，就必须尝试对应指数；范围不含指数时不要顺带取数。

### 4.2 读取后统计

不重复入库。Skill 调用 `get` 读取原始字段和事件后，由返回的 `summary` 统计：

- 有效涨停、20% 涨停、打开跌停、收盘跌停和涨停炸板
- 炸板率、涨跌停比
- 首板数、连板数、连板率、最高板、最高板代表、各高度数量
- 融资余额合计
- 成交额合计
- 三只指数的涨跌点数和涨跌幅

成交额合计 = 上海成交额 + 深圳成交额 + 北京成交额。创业板成交额已包含在深圳成交额中，只作为单独指标展示，不重复计入合计。

融资余额合计 = 上海融资余额 + 深圳融资余额 + 北京融资余额。三项使用同一交易日期；任一缺失则合计留空。

统计结果只基于已保存事件的字段值；Skill 不推断事件是否遗漏。某条事件的 `streak_height` 被修正后，下次显示时重新统计首板、连板数、最高板和连板率。写入更早日期的事件不会自动改写已经保存的后续高度；如需调整，由用户要求 Skill 重新计算或修订。

### 4.3 Skill 获取或用户提供

- 每日涨停和跌停事件
- 上涨家数、下跌家数、中位数涨跌幅、回头波数
- 上海 / 深圳 / 北京融资余额
- 上海 / 深圳 / 创业板 / 北京成交额
- 总市值、流通市值
- 上海 PE（同花顺 `000001`）、深圳 PE（同花顺 `399001`）、创业板 PE（同花顺 `399006`）、全市场 PE
- 平均股价

Skill 可通过 API、网络查询、图片、询问用户或其他可用方式取得这些数据。写入时先确定请求范围（完整复盘，或点名字段/类别），再仅对范围内字段分配来源：范围内未指定来源的字段可自动整理，这些指标属于尽力获取，失败则一次性列出，不得猜测或用前一日数据顶替；范围外字段不取。指定来源只覆盖用户点名、且落在范围内的字段。需要用户提供数据时，一次性给出带单位的 YAML 或表格模板，不逐项对话。用户可以跳过；新记录中跳过的复盘原子字段保存为空值，不得使用 `0` 或前一交易日数据代替。事件 `streak_height` 的缺省处理遵循第 7.4 节，已有记录的跳过语义遵循第 7.5 节。有效涨停数、最高板、连板数等读取后统计的汇总值不能独立入库；图片或文字只提供汇总值时，应提示需要个股事件明细。

### 4.4 每日梯队数据来源

每日梯队不承诺固定自动数据源。Skill 可使用腾讯、东方财富、用户文字、截图、网页抓取或 Agent 其他可用来源，尽力取得事件明细信息。

- 用户指定来源时，只用该来源处理点名范围；未指定来源时，Skill 可自主选择可用来源。
- 日期、股票身份、字段含义或单位无法确认时不写入。
- 多来源冲突时不得猜测；用户明确指定来源时以用户要求为准，否则一次性列出冲突项。
- 只保存成功取得且通过校验的字段；未取得字段留空或保持已有值，不使用其他日期数据替代。
- 数据来源、URL、截图、候选值、采集方式和接口原始响应不入库。

## 5. 总体复盘操作

### 5.1 写入复盘

写入分两阶段：先确定请求范围，再仅对范围内字段分配取数模式。

请求范围：

- 完整复盘：例如“请整理今天的复盘数据”“从这张图片提取复盘数据并保存”。
- 点名字段或类别：例如“补齐两融”“把上涨家数修正为 3210”“从这个链接读取今日两融”。范围外字段不取、不写。

范围内未指定数据源时进入自动整理，例如：

> 请整理今天的复盘数据。

> 生成今天的总体复盘。

> 生成 2026-08-21 的总体复盘。

> 补齐两融。

Skill 确定已收盘交易日后，仅对范围内且未指定来源的字段，主动使用可用来源尽力取得数据，只写入成功取得且校验通过的项，并一次性列出范围内未取得项目。这里的自动是 Agent 自主选择获取方式；第 4.1 节三项是明确自动承诺，请求范围包含哪些指数字段且未指定来源，就必须尝试对应指数；第 4.3 节指标仍属尽力获取。

指定数据或来源时，只处理范围内、且用户点名的数据和来源，例如：

> 从这张图片提取 2026-08-21 的复盘数据并保存。

> 从这个链接读取今日两融数据并保存。

> 600519 今天是四板。

> 把上涨家数修正为 3210。

> 以这张同花顺截图为准，修正市场宽度。

除非用户同时要求扩大范围或把其他数据也自动补齐，否则不另找来源填空。指定来源（含截图）只更新请求允许写入、且来源能明确给出的字段，不清空来源中没有出现的字段。

混合请求先定范围，再按字段分配来源。例如“整理今天复盘，用这张图核对上涨家数”：范围是完整复盘；只有点名的上涨家数走该截图，截图中其他可识别字段不接管；其余范围内字段走自动整理。“补齐两融”范围只有两融，不顺带整理整个复盘。“补齐三大指数”或“补齐上证指数”范围只有对应指数字段，必须尝试通过 `marketdata` 自动获取，不顺带整理整个复盘。“从图片提取复盘数据”范围是完整复盘，可写入图片中全部受支持且能识别的字段。看不清、页面日期与复盘日期不一致、单位不明确、或同一字段多个指定来源冲突时，该字段不入库。

有效涨停数、最高板、连板数等派生汇总值不能独立入库。用户只说“今天最高板是四板”而没有个股明细时，应提示需要个股触板事件；可执行示例是“600519 今天是四板”。

用户可在任意日历日发起请求（包括周末和节假日）。正式记录的业务日期必须是已收盘交易日，见第 9 节。

用户要求写入时，Skill 将本次已经取得或由用户提供的数据经 CLI 写入。不要求所有指标齐全，不保存采集状态，也不为未取得的字段猜测数值。字段级 patch 规则为：

- 未提供字段：保留原值；
- 具体值，包括 `0`：更新；
- 显式 `null`：清空；
- 新记录中未提供的原子字段：保持 `null`。

### 5.2 每日涨跌停事件写入

涨停和跌停事件可以按交易日和方向批量提交，也可以按单股增删改。数据库不保存名单完整性状态，不要求上一交易日已有数据，也不阻止任意历史日期的补录。某日没有对应事件时，所有派生结果均按当前数据库中的零条记录计算。同一「日期 + 市场 + 代码 + 方向」覆盖原事件。方向属于唯一键；若原来保存为涨停、实际是跌停，须调用 `replace_price_limit_event_direction` 在同一事务中删除旧方向并写入新事件，不能只改 `direction`，也不能分开调用删除再保存（新增失败会永久丢失旧事件）。有效涨停数、最高板、连板数等汇总值由读取后统计得到，不能作为独立字段入库。

示例：

```text
未取得以下数据（可跳过）：

- 上海融资余额（元）
- 北京融资余额（元）
```

用户提交后，Skill 校验数值和单位，再调用 package 保存。所有数量字段均为可空整数：`null` 表示缺失，`0` 表示调用方提交的数量为零。数据库不判断该数值是否符合真实市场。最终展示遵循第 6 节：缺失值留空，已保存的 `0` 必须展示。

涨跌停事件的最小 YAML 输入示例：

```yaml
trade_date: 2026-08-21
price_limit_events:
  - market: sh
    code: "600519"
    name: 贵州茅台
    direction: up
    closed_at_limit: true
    limit_rate_bp: 1000
    streak_height: 4
```

事件记录存在即表示盘中曾触及对应方向的涨跌停价。`direction=up, closed_at_limit=true` 表示有效涨停，`false` 表示涨停炸板；`direction=down, closed_at_limit=true` 表示收盘跌停，`false` 表示打开跌停。`streak_height=4` 表示 Skill 取得的该股票在 `2026-08-21` 当天实际为四板，包含当天。炸板或跌停事件写 `streak_height=0`。

### 5.3 显示复盘

用户要求显示时，Skill 只读取数据库并格式化展示，不自动取数、不追问缺失数据、不判断复盘是否“完整”。总体复盘和涨跌停事件按交易日期组合读取：只要任一类数据存在，就返回当日视图；没有 `daily_market_review` 行时原子字段留空，但仍展示已保存的涨跌停事件及其派生指标。两类数据都不存在时，显示“无复盘数据”。

Skill 读取原始字段和事件后，按第 4.2 节统计并按类别格式化展示。读取和展示不修改数据库。

涨跌停比使用“有效涨停数 : 收盘跌停数”的方向展示，不使用百分数。两边都大于 0 时，将较小的一边归一化为 1，倍数保留两位小数：

- 有效涨停 58 只、收盘跌停 15 只，显示 `3.87:1`
- 有效涨停 4 只、收盘跌停 15 只，显示 `1:3.75`
- 两边相等，显示 `1:1`
- 只有一边为 0 时保留真实数量，显示为 `12:0` 或 `0:12`
- 两边都为 0 时，两项数量分别显示 `0`，涨跌停比留空
- 任一基础数据缺失时，涨跌停比留空

### 5.4 保存与查看

同一个交易日只保存一份总体复盘。再次执行时按字段级 patch 更新，不创建重复记录。

用户可以请求查看已保存的历史总体复盘。查询走 `get` 读取原子字段、事件和 `summary`，Skill 再格式化展示；查询本身不修改数据库。

### 5.5 每日梯队的写入、修订与查看

用户要求写入、修订每日梯队或从指定来源提取梯队信息时，Skill 先读取目标日已保存的涨跌停事件，再按用户请求范围写入事件明细字段。事件明细不能脱离父事件单独创建；目标股票没有对应事件时，应先记录完整触板事件，不能只创建梯队明细。

事件明细字段采用 patch 语义：

| 输入行为 | 保存结果 |
| --- | --- |
| 未提供标量或多值字段 | 保持原值 |
| 标量提供具体值，包括 `0`、空逻辑值 `false` | 更新 |
| 标量显式 `null` | 清空 |
| 多值字段提供非空列表 | 按输入顺序整体替换 |
| 多值字段提供 `[]` | 清空列表 |
| 空明细数组 | no-op，不表示清空当日梯队数据 |

`sectors` 和 `limit_up_reasons` 中每一项必须是去除首尾空白后的非空字符串；完全重复的值只保留第一次出现的位置，不自动合并近义词。`limit_up_reasons` 只允许写入 `direction=up` 的事件。

用户只要求查看每日梯队时，Skill 调用 `get` 读取已保存事件、事件明细和 `ladder` 视图，不联网取数、不追问缺失项、不修改数据库。用户可以限定只看二板以上、某一高度、指定股票或指定板块；这些都是读取过滤，不改变保存结构。

## 6. 展示方式

总体复盘按类别使用简单表格展示：

| 指标 | 数值 |
| --- | --- |
| 有效涨停（只） | 52 |
| 炸板率 | 18.75% |
| 上海成交额（亿元） | 8,432.16 |

展示要求：

- 只展示指标和值；
- 单位写在指标名称或数值中；展示层将库内的元换算为亿元或万亿元，将小数形式的比率换算为百分数；
- 不展示采集方式或更新时间；
- 没有对应数据时单元格留空，不显示 `—`、`0` 或其他占位符；
- 已确认的数值为 0 时必须显示 `0`，不能按缺失数据处理；
- 某日没有对应涨跌停事件时，相关事件数量按 `0` 展示；
- 连板梯队按事件中已保存的实际高度动态分组，不生成 `board_1`、`board_2` 等固定字段；
- 每日梯队从最高板到首板展示；同一高度内按 `market + code` 稳定排序，龙头标记不改变顺序；
- 梯队股票可展示板块、涨停原因、竞价占比、开盘涨幅、当日成交额、换手率、龙头标记和备注；多值字段按保存顺序以 ` / ` 连接；
- `is_leader=true` 显示「龙头」，`false` 和 `null` 均留空；
- 涨停炸板、打开跌停和收盘跌停在梯队之后作为独立名单展示；
- 不同类别分别展示。

## 7. 数据存储

### 7.1 数据库定位

Skill 和应用必须通过 `scripts/cli.py` 读写数据库。

默认路径：

```text
~/.marketreview/market_review.sqlite3
```

路径优先级：

```text
CLI --db
> MARKETREVIEW_HOME/market_review.sqlite3
> ~/.marketreview/market_review.sqlite3
```

- Skill 安装目录不保存用户数据；
- 多个 Agent 可各自安装一份 Skill，并共享同一份 `~/.marketreview/` 用户数据；
- 可通过 `MARKETREVIEW_HOME` 或 CLI `--db` 覆盖数据位置。
- 数据表通过 `CREATE TABLE IF NOT EXISTS` 初始化；schema 更新必须保留已有用户数据，涉及已有列变化时使用显式 schema migration。

数据库只保存调用方提交的复盘原子指标、触板事件和事件明细；每条事件直接保存当天的 `streak_height`。数据库不保存名单完整性、数据来源、采集方式、网页证据、候选值或展示汇总字段。Skill 负责通过 API、网络查询或询问用户取得并校验数据；数据库既不关心数据的取得方式，也不判断数据事实是否正确。系统不建立重复的日度聚合表。

### 7.2 单位

数据库统一使用标准单位：

| 类别 | 存储 | 展示 |
| --- | --- | --- |
| 成交额、市值、融资余额 | 元 | 亿元或万亿元 |
| 百分比类指标（中位数涨跌幅、炸板率、连板率、指数涨跌幅等） | 小数，例如 `0.1875` | 百分数，例如 `18.75%` |
| 指数点位、PE、平均股价 | 原单位数值 | 原单位，按附录保留小数位 |
| 个股成交额、竞价额 | 元 | 万元或亿元 |
| 个股价格 | 元/股 | 元，按数据源有效精度展示 |
| 个股换手率、竞价占比、开盘涨幅 | 小数，例如 `0.125` | 百分数，例如 `12.50%` |

融资余额按其业务交易日归属写入对应交易日，即使实际要到 T+1 才公布。不得拿前一日余额冒充当日数据。

### 7.3 核心数据表

| 数据表 | 用途 |
| --- | --- |
| `daily_market_review` | 每个交易日一条总体复盘；只保存原子指标 |
| `daily_price_limit_event` | 一只股票在一个交易日触及一个方向的涨跌停价时一条记录，保存方向、收盘状态、涨跌幅限制和当天连板高度 |
| `daily_price_limit_event_detail` | 与一条触板事件一对一的可空明细；保存个股行情快照、龙头判断和备注 |
| `daily_price_limit_event_sector` | 事件的有序、多值所属板块 |
| `daily_price_limit_event_reason` | 事件的有序、多值涨停原因 |

`daily_price_limit_event` 使用「交易日期 + 市场 + 6 位代码 + 方向」作为唯一键，允许极端情况下同一股票同日分别触及上下限。涨跌停事实独立于总体复盘存在，删除 `daily_market_review` 不删除同日涨跌停事件。

从业务上可以把事件数据理解为 `limit[交易日期][方向][市场 + 股票代码]`：先按交易日分组，再在当日区分涨停方向和跌停方向，最后取得具体股票事件。但 SQL 表不保存嵌套数组，而是将每只股票的每个触板方向平铺为一行。例如：

| `trade_date` | `market` | `code` | `name` | `direction` | `closed_at_limit` | `limit_rate_bp` | `streak_height` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `2026-08-21` | `sh` | `600001` | 示例股份 | `up` | `true` | `1000` | `2` |
| `2026-08-21` | `sz` | `300001` | 示例科技 | `up` | `false` | `2000` | `0` |
| `2026-08-21` | `sh` | `600002` | 示例实业 | `down` | `true` | `1000` | `0` |
| `2026-08-22` | `sh` | `600001` | 示例股份 | `up` | `true` | `1000` | `3` |

查询某个交易日，就是筛选该日期的所有事件行；查询某日涨停方向，就是再增加 `direction=up` 条件。`created_at` 和 `updated_at` 是每行事件的数据库审计时间，不属于独立快照。数据库不建立每日或方向快照表，也不保存 `complete`、已确认零触板或未知等名单状态。

入库身份使用 `(market, code)` 模型：`market` 使用小写 `sh | sz | bj`，`code` 使用保留前导零的 6 位字符串。CLI 返回结果时可组合为 `<market>.<code>`，例如 `sh.600519`、`sz.000001`、`bj.830799`；展示时只显示 6 位代码。写入 API 要求调用方明确提交 `market` 和 `code`，不依赖裸代码猜测市场。不维护证券主表，不因代码是否预先收录而拒绝写入。

Skill 应按第 10 节证券宇宙过滤事件，不提交恒为 `false` 的 `is_st`。package 和数据库不重复复核过滤结果，也不判断某交易日是否漏录股票。

`daily_market_review` 中的指数字段为各指数的当日收盘点位和前收盘点位，不保存涨跌点数和涨跌幅。融资余额和成交额只保存各市场原始值。有效涨停、20% 涨停、打开跌停、收盘跌停、涨停炸板及全部连板汇总均不保存在该表中。

三张事件明细表都以事件身份 `(trade_date, market, code, direction)` 关联 `daily_price_limit_event`。删除事件时级联删除明细信息；删除 `daily_market_review` 不影响事件及明细信息。数据库连接必须启用 SQLite foreign keys。

### 7.4 每日涨跌停事件

一条 `daily_price_limit_event` 的存在表示该股票当日盘中曾触及 `direction` 对应的涨跌停价：

| `direction` | `closed_at_limit` | 业务含义 |
| --- | --- | --- |
| `up` | `true` | 有效涨停，参与首板和连板计算 |
| `up` | `false` | 涨停炸板，不产生当日板数并中断连续性 |
| `down` | `true` | 收盘跌停 |
| `down` | `false` | 打开跌停 |

`limit_rate_bp` 使用整数基点保存当日适用限制，例如 10% 为 `1000`、20% 为 `2000`、30% 为 `3000`。事件表不保存 `touched_at_limit=true`，因为记录存在本身已经表达触板。

`streak_height` 是每条事件最终都填写的整数。用户提供连板数时，Skill 只检查它是整数，然后原样使用；不根据历史记录改写用户值。用户未提供时，Skill 才补齐：有效涨停查找日历前一交易日同股事件，若前一日为有效涨停，则使用前一日已保存的 `streak_height + 1`，否则填写 `1`；涨停炸板、打开跌停和收盘跌停填写 `0`。数据库只保存最终整数，不读取其他日期来推导或判断它是否正确。

展示连板高度时直接读取当日事件保存的 `streak_height`，不回溯或递推，也不产生高度未知状态。用户认为板数有误时，直接修订该事件字段。

### 7.5 同日重跑：保存与修订

同一交易日重复写入时，不做整日覆盖：

| 本轮行为 | 结果 |
| --- | --- |
| 未提供某字段 | 保持原值 |
| 提供具体数值 | 更新，包括合法的 `0` |
| 显式提供 `null` | 清空该字段 |
| 新记录中跳过的字段 | 保存为空 |
| 指定来源未给出的字段 | 保持原值，不清空 |
| 事件列表 | 按事件唯一键保存；已有记录更新，没有则新增 |
| 单股事件修订 | 按交易日、股票和方向更新或删除事件 |
| 事件方向需要从涨停改为跌停（或相反） | 调用 `replace_price_limit_event_direction`，在同一事务中删除旧方向并写入新事件 |
| 事件明细标量未提供 | 保持原值 |
| 事件明细标量为具体值或 `null` | 分别更新或清空 |
| 板块、涨停原因未提供 | 保持原列表 |
| 板块、涨停原因为非空列表或 `[]` | 分别整体替换或清空 |

除原子方向替换接口（`replace_price_limit_event_direction`）外，涨跌停事件不定义 `direction_replace`、`item_patch` 等复杂操作模型。对外只提供直接、普通的保存、查询和删除能力；批量保存只是多行保存的便利接口。空列表表示本次没有行可保存，不代表完整快照，也不额外建立状态。

新增或更新时，Skill 整理 `market`、`code`、`name`、`direction`、`closed_at_limit`、`limit_rate_bp` 和 `streak_height`，经 CLI 完成业务校验后提交。repository 不根据行情、历史事件或证券规则校验这些内容。数据库只执行基本持久化；同一批写入可使用普通事务，目的仅是避免数据库故障造成半批写入，不代表数据库确认数据正确。

方向替换属于事件身份修订。系统必须在同一事务内把旧身份下的明细标量和多值板块迁移到新方向，不因身份修订静默丢失。`limit_up_reasons` 只适用于 `direction=up`：方向改为 `down` 时不迁移该字段。其余内容是否仍适合新方向由用户显式修订或清空。

### 7.6 数据库读写能力

共享数据层只需提供：

- 新增或 patch 指定交易日的总体复盘原子字段；
- 查询单个交易日或日期范围的原子字段；
- 删除指定交易日的总体复盘；涨跌停事件作为共享事实独立保留；
- 保存、更新和删除涨跌停事件；
- 在同一事务中按旧方向删除并写入新方向事件（`replace_price_limit_event_direction`）；
- 查询单日或日期范围内的原始涨跌停事件；
- patch、查询和删除事件明细及其多值板块、涨停原因；
- 读取事件与事件明细后生成单日梯队和炸板、跌停辅助名单；
- 组合查询单日的原子字段和事件；总体复盘或涨跌停事件任一存在即返回，二者都不存在才返回 `None`。

有效涨停、20% 涨停、打开跌停、收盘跌停、涨停炸板、连板高度和其他展示汇总由 Skill 根据查询结果统计。它们不参与数据库写入校验。

### 7.7 每日梯队字段

`daily_price_limit_event_detail` 保存以下可空原子字段：

| 字段 | 存储口径 |
| --- | --- |
| `previous_turnover_amount` | 上一交易日该股票全天成交额，元，非负数 |
| `auction_amount` | 当日开盘集合竞价成交额，元，非负数 |
| `previous_close` | 上一交易日收盘价，元/股，大于 0 |
| `open_price` | 当日开盘价，元/股，大于 0 |
| `turnover_amount` | 当日该股票全天成交额，元，非负数 |
| `turnover_rate` | 当日换手率，按小数保存，非负数 |
| `is_leader` | `true`、`false` 或 `null`；分别表示是、否、未判断 |
| `note` | 人工备注；空白文本规范为 `null` |

`sectors` 可用于所有方向。`limit_up_reasons` 只允许写入 `direction=up` 的事件，包括收盘涨停和涨停炸板；跌停事件写入该字段时整批失败。

板块和涨停原因分别保存在多值子表中，每项包含 `position` 和 `value`。`position` 保留输入顺序；列表为空表示已清空，未提交列表字段表示保留原值。数据库不根据文本自动生成板块层级、概念关系或原因分类。

以下派生字段读取时计算，不入库：

- `auction_ratio = auction_amount / previous_turnover_amount`；
- `open_change = open_price / previous_close - 1`。

任一输入缺失或分母为 `0` 时，对应派生值为 `null`。package 返回小数，Skill 展示时再转换为百分数。

## 8. 技术边界

- 复盘表结构、字段级保存、涨跌停事件持久化、SQLite 查询和读取侧统计放在 `scripts/marketreview/`；
- 事件明细持久化和梯队视图生成放在 `scripts/marketreview/`，由独立 `ladder.py` 负责组合、分组和派生计算；
- 交易日历内置在 `assets/`；
- 最小指数行情能力内置在 `scripts/marketreview/sources/`；
- 数据获取、业务校验、读取后统计和展示流程由 Skill 负责；写入路径的业务校验在 `scripts/cli.py` 执行；
- CLI 不提供复杂的外部采集编排接口；
- 数据库使用 SQLite；
- 公共字段使用 `snake_case`。
- 不保存分时序列、日 K 序列、走势图图片或外部行情接口原始响应。

## 9. Skill 的交易日与收盘校验

Skill 只为已收盘交易日生成正式记录。用户可以在非交易日运行 Skill，但 CLI 写入路径会拒绝非交易日落库。该规则属于业务校验；repository 和 SQLite 本身不查询交易日历。

- 未指定日期时，落到最近一个已收盘交易日；
- 用户显式指定非交易日：不落库，并提示最近交易日；
- 目标日为当日且尚未收盘：拒绝生成正式记录；
- 历史已收盘交易日可直接写入或修订；
- 日度复盘统一以 A 股 15:00 作为收盘边界。

内置交易日历使用统一的 A 股交易日合同，北交所与沪深交易日一致。系统不允许单独为北交所创建另一条当日记录。

## 10. 复盘证券宇宙与 ST 排除

涨跌停与连板的证券宇宙为上海、深圳、北京交易所上市的人民币普通股票。Skill 获取数据时排除 B 股、ETF、基金、债券、可转债、退市整理股票、上市首日及当日无涨跌幅限制的股票，同时排除 ST 股票。该过滤不在 repository 或 SQLite 中重复执行。

具体口径：

- 排除交易日当日处于 `ST`、`*ST` 等特别处理状态的股票；
- 有效涨停、20% 涨停、打开跌停、收盘跌停、涨停炸板均不统计 ST 股票；
- 昨日有效涨停分母和每日涨跌停事件也不统计 ST 股票；
- Skill 不主动提交 ST 股票事件；
- 连板高度只计算连续的、符合复盘证券宇宙条件的非 ST 涨停交易日；
- 股票进入 ST 状态时原连板连续性终止；以后撤销 ST 后再次涨停，应重新从一板起算；
- ST 判断以对应交易日的历史状态为准，不能使用股票当前名称或当前 ST 状态回填历史数据；
- ST 判断使用按交易日生效的 `is_st` 或证券状态字段，不依赖临时的名称字符串。

因此，所有涨跌停派生指标也自然排除 ST：

- 炸板率的分子和分母均不含 ST；
- 涨跌停比两侧均不含 ST；
- 连板率的分子与上一交易日有效涨停分母均不含 ST。

市场宽度、成交额、市值、PE 等直接录入或全市场口径的指标，仍以证券软件展示为准；Skill 提交每日涨跌停事件前按上述证券宇宙口径过滤。数据库不会复核该过滤是否正确。

### 10.1 涨跌停细分口径

- `20% 涨停` 统计创业板和科创板中适用 20% 涨跌幅限制且收盘涨停的非 ST 股票。
- 北交所适用 30% 涨跌幅限制的非 ST 股票，计入有效涨停、打开跌停、收盘跌停和涨停炸板等相应基础数量，但不计入 `20% 涨停`；系统不单独设置 `30% 涨停` 展示项。
- 当日盘中打开后重新封住涨停且收盘仍为涨停，计入有效涨停，不计入涨停炸板。
- 当日曾触及涨停但收盘未封住，计入涨停炸板。

### 10.2 连板连续性

- 首板和所有连板都来自每日有效涨停事件保存的 `streak_height`。
- 每一个连续交易日都必须属于上述证券宇宙并收盘涨停；停牌、收盘未涨停、进入 ST、进入退市整理期或出现无涨跌幅限制交易日，均中断连板。
- 炸板后回封并以涨停收盘，仍视为当日涨停，连板可以延续；收盘未封住则中断。
- 连板率固定使用「今日二板及以上非 ST 股票数 ÷ 上一交易日非 ST 有效涨停数」。
- 用户提供当日连板数时，Skill 直接采用；用户未提供时，前一交易日存在同股有效涨停事件则使用其已保存高度加一，否则填写首板 `1`。
- 炸板或未涨停后重新起算；这一计算只发生在 Skill 准备写入且用户未提供高度时，数据库不负责计算。

### 10.3 事件数据的责任

系统保存 Skill 取得并完成业务校验的触及涨停或跌停股票，不声明某交易日名单完整，也不推断是否漏录。Skill 负责证券宇宙、市场、代码、方向、收盘状态、涨跌幅限制以及缺省连板高度的计算；CLI 写入路径校验市场、代码、方向和涨跌幅限制，repository 和数据库原样持久化最终提交内容，不复核行情事实或历史连续性。没有某条事件时，展示统计按数据库中不存在该事件处理。

有效涨停、20% 涨停、打开跌停、收盘跌停、涨停炸板和连板汇总不接受独立手工聚合值，统一从事件计算，从数据结构上消除聚合值与个股名单不一致的问题。

repository 不根据股票名称推断历史 ST 状态，也不独立复核调用方的历史证券宇宙过滤结果。

## 11. 验收标准

### 11.1 总体复盘与涨跌停事件

1. 用户未指定日期且在非交易日或盘前发起时，使用最近一个已收盘交易日；用户显式指定非交易日时不落库并提示最近交易日；用户显式指定尚未收盘的当日时拒绝生成正式记录。
2. 自动获取仅承诺三只指数的日 K；成功则写入收盘与前收盘，失败不覆盖原值、不用其他日期顶替。
3. 用户要求写入时，Skill 只写入该请求取得或由用户提供的数据；复盘原子字段和涨跌停事件支持修订，不保存名单完整性状态。
4. 涨跌停基础数量、炸板率、涨跌停比、首板与连板汇总、连板率、融资余额合计、成交额合计、指数涨跌点数和涨跌幅均由 Skill 读取后统计，不入库。
5. 数据库只保存原子字段；同一交易日重复执行不产生重复记录，并遵守字段级 patch。
6. 用户要求显示时，Skill 只读取和格式化已保存的复盘，不自动取数、追问或修改数据库；原子字段为 `null` 时留空。
7. 总体复盘按照八个类别以简单表格展示，表格只显示指标和值。
8. 默认数据库路径为 `~/.marketreview/market_review.sqlite3`。
9. 数据层支持总体复盘和涨跌停事件的简单新增、查询、更新与删除，支持按单日和日期范围查询，可被 Skill 之外的应用调用。
10. 涨跌停和连板指标只基于当前已保存事件计算；没有事件时相应数量为 `0`，系统不判断是实际为零还是尚未录入。
11. `daily_price_limit_event` 使用日期、市场、代码和方向作为唯一键；事件独立于总体复盘，删除总体复盘不删除同日事件事实。方向变更须通过 `replace_price_limit_event_direction` 原子替换，不能只改 `direction`，也不能依赖非事务的先删后写。
12. 数据库不保存数据来源或采集方式。
13. 写入先确定请求范围，再对范围内字段区分自动整理和指定来源；范围外字段不取。指定来源请求不得把未点名或范围外指标用其他来源悄悄补上，除非用户同时要求扩大范围或自动补齐。混合请求中，用户点名用某截图核对的字段才走该截图，截图中其他可识别字段不接管。
14. 看不清、页面日期与复盘日期不一致、单位不明、同一字段多来源冲突，或仅有最高板/有效涨停等派生汇总值而没有个股事件明细时，对应内容不入库。
15. `2026-08-21` 已由仓库沪深交易日历确认为已收盘交易日，前一交易日固定为 `2026-08-20`。黄金 fixture 至少包括连续多个交易日的涨停事件、当日跌停事件、首板、连板、涨停炸板、打开跌停、收盘跌停、用户提供高度和 Skill 缺省计算高度，以及所有展示统计预期结果。
16. Skill 验收覆盖用户提供高度时原样采用、未提供且前日有效涨停时高度加一、无前日有效涨停时写首板 `1`，以及炸板和跌停写 `0`；展示直接读取已保存高度，不回溯计算。
17. 持久化验收覆盖事件新增、更新、查询和删除，以及数据库故障时批量写入不会留下半批数据；业务内容正确性由 Skill 和用户负责。

### 11.2 每日梯队

1. 每日梯队只读取现有有效涨停事件生成，首板进入高度 `1` 分组，不保存重复名单或高度聚合。
2. 梯队按实际高度降序分组；同高度按市场和代码稳定排序，最高高度不受 11 板限制。
3. 事件明细支持昨日成交额、竞价额、昨日收盘价、开盘价、当日成交额、换手率、三态龙头判断和备注。
4. 所属板块与涨停原因支持有序多值；未提交保留、非空列表整体替换、空列表清空。
5. 竞价占比和开盘涨幅读取后计算，不入库；输入缺失或分母为 `0` 时留空。
6. 梯队明细采用字段级 patch，正确区分未提交、`null`、`0` 和 `false`。
7. 事件明细只能关联已存在事件；批量写入任一条失败时整批回滚。
8. 删除事件级联删除事件明细；方向替换在同一事务内迁移明细标量和板块；改为跌停时不迁移 `limit_up_reasons`。
9. `get` 返回 `ladder`，其中包含梯队、涨停炸板、打开跌停和收盘跌停名单。
10. 每日梯队数据可由腾讯、东方财富、用户文字、截图、网页抓取或 Agent 可用来源取得，但不承诺固定来源，也不保存来源信息。
11. 只读梯队请求不联网补数、不追问、不修改数据库。
12. schema 更新不得损坏已有数据；测试覆盖 schema、patch、事务、分组、派生计算和 CLI 黄金结果。

## 12. 范围边界

- 不处理午间数据、开盘情绪和情绪周期阶段判断。
- 涨跌停事件、市场宽度、两融、市场成交额、市值、PE 和平均股价不承诺专用自动采集 provider；Skill 可通过可用来源取得数据后提交。
- 不承诺腾讯、东方财富或其他固定 provider 的可用性，不保存分时、日 K、走势图图片或行情接口原始响应。
